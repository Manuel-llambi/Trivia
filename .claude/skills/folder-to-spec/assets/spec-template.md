## Source

The folder or repository the spec was built from, and the key documents it relied on (by name, not full path).

## Problem Statement

The problem that the user is facing, from the user's perspective.

## Solution

The solution to the problem, from the user's perspective.

## User Stories

A LONG, numbered list of user stories covering every flow, state, and edge case the source material describes. Format:

1. As an <actor>, I want a <feature>, so that <benefit>

Example:

1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending

## Implementation Decisions

Decisions found in the material, such as:

- Modules to build or modify, and their interfaces
- Architectural decisions
- Schema changes
- API contracts
- Specific interactions, states, and animations described in mockups or definitions

No file paths or code snippets, except decision-rich snippets from the source, trimmed and marked as coming from the source folder.

## Testing Decisions

- What makes a good test: only external behavior, not implementation details
- Which modules will be tested, and at which seams
- Prior art: similar tests in the folder, if any

## Open Questions

Every gap found while reading: things the spec needs but the material does not decide. Mark each as **blocking** or **non-blocking**.

## Out of Scope

What the material explicitly excludes, plus anything deliberately left out and why.

## Further Notes

Synonyms found for the same concept, contradictions between documents (and which one was followed), and anything else worth knowing.
